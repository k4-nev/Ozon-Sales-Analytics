## 1. Назначение приложения

Настольное/веб-приложение для аналитики продаж продавца на маркетплейсе **Ozon**.

- **Вход:** CSV-выгрузка заказов из личного кабинета Ozon Seller (отчёт «Доставки FBO» — 37 колонок; в ранней ветке — упрощённый CSV из 4 колонок).
- **Выход:** аналитика по каждому товару и сводно по магазину:
  - продажи по времени суток (в какие часы больше заказов);
  - сумма дохода по дням (сумма отправления и оплачено покупателем);
  - чистая прибыль (калькулятор по SKU с себестоимостью, комиссиями, налогом, рекламой, возвратами, статусами);
  - доставки по кластерам/регионам.
- **Формат:** один самодостаточный HTML-файл (весь CSS и JS инлайн, без внешних зависимостей и CDN). Он же оборачивается в Windows **.exe** через Electron.
- **Хранение:** локальное. Профили магазинов, настройки и данные — на устройстве (в .exe — файлы в `%AppData%`, в браузере/ранней ветке — localStorage). Сети нет.

## 5. Архитектура (общая)

- **Один HTML-файл** = весь продукт: `<style>` (инлайн CSS с CSS-переменными) + разметка-обёртка (`#app`, `#toast`, скрытый `#fileInput`) + большой `<script>`.
- Рендер — строковый: функции `*View()` возвращают HTML-строки, вставляются в `#app`, затем `wire*()` навешивают обработчики. Ключевой цикл — `render()` → `renderMain()`.
- Состояние — глобальные переменные (`DATA`, `selectedSku`, `activeTab`, `selectedPeriodDays`/`sortMode`, `PROFILES`, `activeId`, `query`, `drawerOpen` и т.д.).
- `store`-абстракция скрывает хранилище: в .exe это `window.fileStore` (файлы в `%AppData%`), иначе — localStorage.
- Экспорт картинок: отчёт строится как **SVG** (`build*ExportSVG`), затем рисуется на canvas и отдаётся как PNG (`renderReportBlob`).

Логические разделы `<script>` (по комментариям-заголовкам): CORE LOGIC (парсер, периоды, агрегация, калькулятор) → CHART DRAWING (SVG-примитивы) → STATE → STORAGE/PROFILES → RENDER (views) → WIRING → EXPORT → HELPERS → INIT.

## 6. Модель данных и парсер CSV (линия A)

**`parseCSVText(text)`** — полноценный CSV: кавычки, экранирование `""`, разделители `;` и переводы строк внутри кавычек, срез BOM. Разделитель — `;`.

**`parseDateAny(dt)`** — поддерживает ISO `YYYY-MM-DD HH:MM:SS` и `dd.mm.yyyy HH:MM`. Возвращает `{serial (UTC-день), hour, dayKey}`.

**`processCSV(text)`** — колонки ищутся ПО ИМЕНИ заголовка (порядок и лишние колонки не важны):
- `Принят в обработку` (дата/час), `Название товара`||`Название`, `SKU`, `Количество`,
- `Сумма отправления`, `Оплачено покупателем`,
- `Кластер доставки` → fallback `Регион доставки` → `Город доставки` → `Не указан`,
- `Статус`.

**Категория статуса — `statusCat(status)`:**
- возврат `'c'`: `/отмен|возврат|отказ/i` (Отменён, Возврат, Отказ);
- доставлен `'d'`: `/^доставлен/i` (именно «Доставлен», НЕ «Доставляется»);
- в обработке `'p'`: всё остальное (Доставляется, Ожидает отгрузки, Ожидает сборки…).
- Если колонки `Статус` нет → всё считается доставленным (`'d'`).

**Структура результата:**
```
products: [{ sku, name, recs: [{ d:dayIndex, h:hour, q:qty, sh:ship, pd:paid, cl:cluster, st:'d'|'p'|'c', x:cancelled0/1 }] }]
meta: {
  days:[{key,label}], spanDays, anchorIdx,
  periodOptions:[{days,label}],
  productCount, totalOrders, totalQty, shipTotal, paidTotal,
  returnsCount, processingCount, deliveredCount,
  minDate, maxDate
}
```
`name` товара = самый частый вариант названия для этого SKU. `recs` — «сырые записи» (нужны для гибкого периода и статусов). День `d` — индекс в общей оси дней `meta.days` (от минимальной до максимальной даты включительно).

> Важно: профили, сохранённые до 1.4 (без `recs`/статусов), нужно один раз перезагрузить из CSV.

## 7. Периоды и оконная агрегация (линия A)

**`periodOptions(span)`** — набор вариантов зависит от диапазона файла. `S = min(spanDays, 90)` (максимум 3 месяца). Берём стандартные `[7 Неделя, 14 «2 недели», 30 Месяц, 60 «2 месяца», 90 «3 месяца»]`, у которых `days < S`, и добавляем финальный «полный» вариант на `S` дней (подписывается стандартным именем, если совпало, иначе «за N дней»).
Примеры: неделя → `[Неделя]`; месяц → `[Неделя, 2 недели, Месяц]`; 3 мес → `[…, 2 месяца, 3 месяца]`; 18 дней → `[Неделя, 2 недели, «за 18 дней»]`.

**Глобальный период** `selectedPeriodDays` применяется ко ВСЕМ вкладкам (вынесен в шапку, single-select). Сохраняется в `CHART_KEY` как `{period}`. `clampPeriod()` подгоняет значение под опции загруженного файла.

**`computeAgg(recs, N)`** — окно = последние `N` дней от конца (`fromIdx = D - N`). Возвращает:
- `hourly[24]` — все статусы (это статистика ИНТЕРВАЛОВ времени — возвраты тоже имеют вес);
- `ship[]`, `paid[]` по дням — все статусы;
- `clusters{}` — все статусы;
- `qty/shipTot/paidTot` — все статусы;
- `returns{count,qty,ship,paid}` — только отменённые;
- `delivered{count,ship,paid,qty}`, `processing{count,ship,paid,qty}`;
- `labels`, `minDate`, `maxDate`.

`winCache()` мемоизирует агрегаты по каждому SKU для текущего периода (`DATA._win`). `currentView()` — агрегат выбранного товара или «Весь магазин» (конкатенация recs).

## 8. Калькулятор чистой прибыли — формулы (линия A)

Источник логики: `ozon-profit-module-spec.md` + `ozon-fbo-calculator.jsx` (референс).
Реализация: `profitFor(sku, view)`. **Реальная прибыль считается ТОЛЬКО по доставленным**;
«в обработке» (processing) показывается отдельно; возвраты списывают комиссии.

Входные суммы берутся из данных за период:
- `price` (выручка) = `delivered.ship` (Сумма отправления доставленных);
- `paid` = `delivered.paid` (Оплачено покупателем доставленных);
- `qty` = `delivered.qty`.

Ставки: `feeMin/feeMax` по модели (`fbo` → fboMin/fboMax, `fbs` → fbsMin/fbsMax), `avg=(min+max)/2`.

Расчёт по ставке `feePct` (на выручку `price`, количество `qty`):
```
fFee  = feeOff ? 0 : price * feePct/100
fAds  = adsOff ? 0 : price * ads/100
fCogs = cogsOff? 0 : cogs * qty        // cogs — себестоимость ЗА ЕДИНИЦУ
pbt   = price - fFee - fAds - fCogs
tax:
  usn6  → price * 0.06
  usn15 → max(pbt*0.15, price*0.01)    // минимальный налог 1% с выручки
  other → price * otherRate/100
  none  → 0
net   = pbt - tax
```
- `main = run(avg)`, диапазон `run(feeMax)…run(feeMin)` (если ставка плавающая → пометка «≈»).
- **Возвраты:** `retCost = (feeOff?0:returns.ship*avg/100) + (adsOff?0:returns.ship*ads/100)`. Отменённые оплатили комиссию Ozon и рекламу, но не принесли выручки (себестоимость вернулась). Итог: `net = main.net - retCost`.
- **«В обработке»:** `pendingNet = run(avg)` на `processing.ship`/`processing.qty` — показывается отдельно, в финал не входит.
- Метрики: `margin = net/price`, `roi = net/(cogs*qty)`, безубыточная себестоимость на единицу (`breakeven`).
- Блок баллов/соинвеста: если `!paidOff` и `0 < paid < price` → распределение (баллы не меняют итог, лишь перекладывают расходы).

**CALC_DEFAULTS:** `{paidOff:true, model:'fbo', fboMin:47, fboMax:49, fbsMin:45, fbsMax:50, feeOff:false, cogs:null, cogsOff:false, ads:15, adsOff:false, taxMode:'usn6', otherRate:1.5}`.
Ввод сохраняется **по SKU глобально** (`calcData` → `CALC_KEY`), подтягивается в любом профиле с тем же SKU.
`calcComplete(sku)` = запись есть && `!cogsOff` && `cogs>0`.

**Эталонные примеры (проверены, сходятся):**
- A: price=1000, fbo 47/49, ads=15, cogs=400, УСН6 → **net = −90**
- B: то же, УСН15 → **−40** (сработал минимальный 1%)
- C: price=1500, УСН15 → **131.75**
- D: A + оплачено 700 (баллы) → net −90, блок баллов покрывает часть комиссии
- E: price=1000, ads=15, cogs=200, «Другое» 1.5% → **155**

**Сводный отчёт «Весь магазин» (вкладка прибыли):** горизонтальные полосы по возрастанию,
убытки красным, ИТОГО. Показаны только товары с полностью заполненным калькулятором («N из M»).

## 9. Вкладки и UI (линия A)

Детализация товара / «Весь магазин» — 4 вкладки (глобальный период сверху действует на все):
1. **Кол-во продаж по времени** — один почасовой график за выбранный период (все статусы) + пометка «доставлено X · в обработке Y · возвраты Z».
2. **Сумма дохода за промежуток** — два графика по дням (Сумма отправления / Оплачено покупателем) + пометка статусов/возвратов. При большом числе дней график расширяется и скроллится по горизонтали (≤16 дней — адаптивно без скролла).
3. **Чистая прибыль** — по товару: калькулятор (ввод) + водопад расходов + чистая прибыль + строка «Ещё N ₽ в обработке»; выручка/оплата показывают полную сумму с «из них N ₽ в обработке». Для «Весь магазин» — сводный отчёт (см. выше).
4. **Кластер доставки** — горизонтальный рейтинг регионов (все статусы) + пометка возвратов.

Экспорт PNG/копирование работают по активной вкладке (`build{Time,Income,Profit,Cluster}ExportSVG`).

Боковой список товаров: сортировка Продажи ↓ / Продажи ↑ (в ветке B добавлена «Своя»). Слева «Весь магазин».
Профили — в выезжающем drawer (создание, удаление с инлайн-подтверждением, поиск).

## 10. Статусы заказов (линия A) — сводка правил

- **Считаем ВЕЗДЕ все строки** (время, доход, кластеры) — с пометкой числа возвратов.

## 11. Импорт/экспорт данных (линия A)

Один файл-бэкап со всеми данными (профили + настройки калькулятора по SKU + настройки).
- `gatherExport()` → `{ app:'ozon-analytics', version, exportedAt, index, active, charts, calc, profiles:{id:rawJSON} }`.
- **Экспорт:** в .exe — системный диалог «Сохранить как» (`window.fileStore.exportFile` → IPC `dialog:save`); в браузере — download blob.
- **Импорт:** предупреждение (`confirm`) → диалог/файл-инпут → `applyImport()`: мёрж индекса профилей по `id`, запись данных профилей, мёрж калькулятора по SKU. Затем перезагрузка состояния и рендер.
- Кнопки: в drawer (низ) и на стартовом экране (когда нет профилей).

## 12. Ветка 1.2 (линия B) — отличия и режим «Своя»

Отличия от линии A: простой парсер `splitRow` (колонки `дата ; название ; SKU ; количество`),
фиксированные графики `CHART_DEFS` (неделя/3 недели/месяц), НЕТ дохода/кластеров/прибыли/статусов/периода/облака,
хранение — **напрямую localStorage** (без `window.fileStore`).

**Добавлено (последняя работа) — сортировка «Своя» + drag&drop:**
- Кнопка «А–Я» заменена на **«Своя»** (`sortMode='custom'`).
- «Своя» стартует как сортировка по продажам, но карточки можно перетаскивать за ручку-«захват» (`.drag-handle`, иконка `GRIP`), появляющуюся только в этом режиме у правого края.
- Анимация — FLIP: перетаскиваемая карточка `position:fixed` следует за курсором, остальные плавно расступаются, на отпускании — плавно встаёт; используется placeholder (`.drag-ph`).
- Порядок хранится в `DATA.order` (массив SKU) внутри данных профиля → сохраняется в профиле и на устройстве (localStorage), переживает перезапуск. При перезагрузке CSV в тот же профиль порядок сохраняется по SKU; новые товары встают в конец по продажам.
- **Профили тоже перетаскиваются** (в drawer, ручка у каждой строки, `data-pid`) → меняется порядок массива `PROFILES`, сохраняется через `saveProfilesIndex()`.
- При активном поиске drag выключен (чтобы не путать порядок в отфильтрованном списке) — есть подсказка.
- Движок: `enableDragSort(container, itemSel, onReorder)`, `flipReorder(...)`, `startDrag(...)`, обработчики `onProductsReordered`/`onProfilesReordered`. Клик по карточке/профилю игнорируется во время drag (флаг `dragActive`).
- **TODO ветки:** нет авто-скролла списка при подтаскивании к краю (длинный список — сначала прокрутить). При будущей сборке .exe из этой ветки нужно вернуть файловый мост `window.fileStore` (как в 1.2.0), иначе данные будут только в localStorage Electron.

## 13. Хранилище и ключи

- `analyse_profiles_v1` — индекс профилей (массив `{id,name,productCount,minDate,maxDate,...}`).
- `analyse_profile_<id>` — данные профиля (`{products, meta, savedName, savedAt, order?}`).
- `analyse_active_profile_v1` — активный профиль.
- `analyse_charts_v1` — линия A: `{period}`; ветка B: `{week,three,month}`.
- `analyse_calc_v1` — **только линия A**: калькулятор по SKU (`{SKU: {inputs}}`), глобально (вне профилей).
- `STORE_KEY` (легаси одиночного магазина) — миграция в профиль при первом запуске.

`PKEY(id) = 'analyse_profile_'+id`. Данные профиля кэшируются в `memData`.

## 14. Сборка .exe (Electron + electron-builder, под Linux через wine)

Проект сборки: каталог `app-build/` (в этом окружении — `/home/claude/app-build`). Состав:

Проверка бандла без запуска: читать `dist/win-unpacked/resources/app.asar` как latin1 и grep по ASCII-маркерам
(кириллица в asar даёт ложные пропуски — искать по латинским идентификаторам функций).

Важно:

## 15. main.js / preload.js (линия A)

**preload.js** (contextBridge → `window.fileStore`):
```js
get(key)          -> ipcRenderer.sendSync('store:get', key)
set(key,value)    -> ipcRenderer.sendSync('store:set', {key,value})
remove(key)       -> ipcRenderer.sendSync('store:remove', key)
exportFile(name,text) -> ipcRenderer.invoke('dialog:save', {name,text})
importFile()          -> ipcRenderer.invoke('dialog:open')
```
**main.js:** окно с `contextIsolation:true` + preload. Файловый стор в `app.getPath('userData')/store`
через `ipcMain.on('store:get'|'store:set'|'store:remove', … sendSync)`. Диалоги —
`ipcMain.handle('dialog:save', …)` (showSaveDialog + `fs.writeFileSync`) и
`ipcMain.handle('dialog:open', …)` (showOpenDialog + `fs.readFileSync`), фильтр `*.json`.
Рендерер сам выбирает `window.fileStore` или localStorage.

## 17. Ключевые решения и соглашения

- **Отменённые считаются во всех вкладках** (время/доход/кластеры) — они важны как интервалы; в прибыли — отдельная логика (только доставленные, обработка отдельно, возвраты списывают комиссии).
- Прибыль — **на суммах за период** (агрегат), себестоимость — на единицу × количество. Прибыль приблизительная (ставка Ozon плавающая), финал — в кабинете.
- Один самодостаточный HTML, без внешних зависимостей/CDN. Всё локально, без сети.
- Никогда не использовать localStorage/sessionStorage внутри «артефактов» превью — но в скачанном файле/.exe localStorage работает (об этом всегда предупреждать заказчика).
- Русский интерфейс; тёплый, простой тон; заказчик ведёт продуктовые решения уверенно.
- Отложенные фичи держать за флагами/в отдельных спеках, не мешать основному потоку.
